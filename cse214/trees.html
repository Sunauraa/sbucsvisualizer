The four rotation cases

After an insert, exactly one node is the lowest unbalanced one. Which rotation you need depends on the direction of the two steps down toward the new key:

Casebf(node)bf(child)Fix
Left-Left+2≥ 0single right rotation
Left-Right+2< 0left on child, then right
Right-Right−2≤ 0single left rotation
Right-Left−2> 0right on child, then left

A rotation is a local pointer swap — O(1) — and it never changes the in-order sequence, which is why the BST property survives. Insert needs at most one (double counts as one); delete may need one at every level.

Overflow, underflow, and why heights match

Multiway trees never rotate. They keep all leaves at the same depth by changing the number of keys in a node instead of moving nodes around:

overflow
too many keys after an insert → split, middle key goes up
underflow
too few keys after a delete → transfer from a sibling that has spare keys
no spare keys
→ fusion: merge two siblings plus the separator into one node
grows taller
only when the root splits — so all leaves rise together
grows shorter
only when the root is emptied by a fusion

In a (2,4)-tree, height is between log₄n and log₂n. A B-tree of order m has height ≤ log⌈m/2⌉n — with m = 100, a million keys fit in 3 levels.

A (2,4)-tree and a red-black tree are the same thing wearing different clothes: colour a 3-node's extra key red and you get one from the other. AVL trees are more rigidly balanced (faster lookups), red-black/(2,4) trees do less work per update (faster writes).
